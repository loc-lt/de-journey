# Project 04 - SQL

# **Overview**

Your task is to **generate and insert synthetic transactional data** into two tables — `order` and `order_item` You will use existing data from the following tables (created in Project 03):

- `brand`
- `category`
- `seller`
- `customer`
- `product`
- `promotion`
- `promotion_product`

# **TASK**

## **1. Create table follow schema and populate data**

### **🧾 `order`**

| Column | Type | Constraint | Description |
| --- | --- | --- | --- |
| `order_id` | SERIAL | PRIMARY KEY | Unique order ID |
| `customer_id` | INT | FK → customer(customer_id) | Customer who placed the order |
| `order_date` | TIMESTAMP | — | When order was placed |
| `status` | VARCHAR(20) | CHECK (status IN ('PLACED','PAID','SHIPPED','DELIVERED','CANCELLED','RETURNED')) | Order status |
| `total_amount` | DECIMAL(12,2) | CHECK (total_amount >= 0) | Total order value |
| `created_at` | TIMESTAMP | CHECK (created_at >= order_date) | Record creation |

> **Note:** Seller information is derived from `order_item` → `product` → `seller`. There is no `seller_id` on the order table (see Project 03 schema).
> 

### **📋 `order_item`**

| Column | Type | Constraint | Description |
| --- | --- | --- | --- |
| `order_item_id` | BIGSERIAL | PRIMARY KEY | Unique line item ID |
| `order_id` | INT | FK → "order"(order_id) | References the parent order |
| `product_id` | INT | FK → product(product_id) | References the purchased product |
| `order_date` | TIMESTAMP | — (denormalized for partition) | Copied from order — enables partition by month |
| `quantity` | INT | CHECK (quantity > 0) | Number of units purchased |
| `unit_price` | DECIMAL(12,2) | CHECK (unit_price > 0) | Price per unit at the time of purchase |
| `subtotal` | DECIMAL(12,2) | CHECK (subtotal = quantity * unit_price) | Calculated as `quantity * unit_price` |
| `created_at` | TIMESTAMP | CHECK (created_at >= order_date) | Record creation |

### **Data Requirements**

- **Orders volume**:
    
    Generate **5,000,000 records** in the `order` table (~1M orders/month).
    
- **Order items volume**:
    
    Each order should contain **between 2 to 5 random products** (avg 3.5).
    
    → 5M orders × 3.5 items = approximately **17,500,000 order_items** rows.
    
    - Each `customer_id` must reference a valid customer from the `customer` table.
    - Products should be randomly selected from the existing `product` table
    - **Date range**: The `order_date` must be distributed evenly between **January 1, 2025** and **May 31, 2025**.

## **🐝 *Hint:***

- **Order amount**:
    
    The `total_amount` in `order` should equal the **sum of all `subtotal` values** from its related order items.
    
- **Status distribution (recommended)**:
    - **2% → `PLACED`**
    - **10% → `PAID`**
    - **60% → `DELIVERED`**
    - **20% → `SHIPPED`**
    - **5% → `CANCELLED`**
    - **3% → `RETURNED`**
- **Data Distribution:**
    - `customer_id`: Pareto — 20% of customers generate 80% of orders.
    - `product_id` in `order_item`: Pareto — some products are bestsellers.

## **2. Optimization techniques**

- Write query for listing requirement and snapshot the result (run time and execution plan)
    - Total revenue per month
    - Orders filtered by seller and date
    - Filter data in `order_item` by product_id
    - Find order with highest total_amount
    - List products with highest quantity sold
    - Orders by Seller in March 2025
    - Revenue per Product per Month
    - Products Sold per Seller
- Create monthly partitions (Jan–May 2025) for the two tables above and create an index on the `product_id` column of `order_item` table.
    - 💡 **Hint (PostgreSQL):**
        
        If you encounter the error `ERROR: unique constraint on partitioned table must include all partitioning columns`, remember that in PostgreSQL declarative partitioning, the partition key must be part of the Primary Key constraint! Think about composite primary keys `(order_id, order_date)`.
        
- Re-run the queries for the requirements above and take a snapshot of the results. Compare the detailed execution plans before and after optimization.

### **Monthly Revenue Report**

- **Goal:** Show total revenue and total orders per month.
- **Columns:** `month`, `total_orders`, `total_quantity`, `total_revenue`
- **Filter:** Orders within a specific date range (`start_date` to `end_date`)

### **Daily Revenue Report**

- **Goal:** Show total revenue and total orders per day.
- **Columns:** `date`, `total_orders`, `total_quantity`, `total_revenue`
- **Filter:** Orders within a specific date range (`start_date` to `end_date`) and *product list*

### **Seller Performance Report**

- **Goal:** Compare sellers by total revenue and quantity sold.
- **Columns:** `seller_id`, `seller_name`, `total_orders`, `total_quantity`, `total_revenue`
- **Filter:** Orders within a specific date range. Optional filter by `category_id` or `brand_id`.

### **Top Products per Brand**

- **Goal:** Identify top products for each brand by quantity sold.
- **Columns:** `brand_id`, `brand_name`, `product_id`, `product_name`, `total_quantity`, `total_revenue`
- **Filter:** Orders within a specific date range. Optional filter by *seller list.*

### **Orders Status Summary**

- **Goal:** Count orders per status (completed, pending, cancelled).
- **Columns:** `status`, `total_orders`, `total_revenue`
- **Filter:** Orders within a specific date range; optionally filter by seller list or category list.
